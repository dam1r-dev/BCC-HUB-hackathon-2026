# Критерии качества требований

Источники: ISO/IEC/IEEE 29148:2018 п. 5.2.5 (отдельное требование), п. 5.2.6 (набор требований); IEEE Std 830-1998 п. 4.3.

## Свойства отдельного требования (поле criterion)

- **necessary** — необходимость. Требование нужно для цели продукта; без него чего-то не хватит. Нарушение: требование ни к чему не ведёт, дублирует другое.
- **appropriate** — уместный уровень. Требование говорит «что», а не «как»; нет лишних проектных решений (конкретные технологии, классы, методы HTTP без обоснования). Нарушение: навязанная реализация, которая к тому же ошибочна или рискованна.
- **unambiguous** — однозначность. Формулировку можно понять только одним способом. Нарушение: неопределённые термины и статусы объектов, неуказанный часовой пояс или единицы, значение без уточнения какое именно, размытые слова («быстро», «удобно», «при необходимости»).
- **complete** — полнота. Описаны все условия, граничные случаи, ошибки, единицы. Нарушение: не описано поведение при отмене или корректировке, при отключении функции, при ошибке; пустые разделы; пропущены статусы ответа.
- **singular** — единичность. Одно требование — одна мысль. Нарушение: несколько независимых условий в одном пункте, которые нельзя проверить отдельно.
- **feasible** — выполнимость в разумных рамках.
- **verifiable** — проверяемость. Есть объективный способ проверить выполнение (число, порог, точка отсчёта, метод измерения). Нарушение: срок без точки отсчёта и доли событий («в течение N секунд» — от какого события, для какой доли запросов); нет критериев приёмки.
- **correct** — корректность. Требование верно отражает потребность; пример/значение не ошибочны; описание соответствует сути (например, название операции говорит одно, а описание — другое).
- **conforming** — соответствие стандарту/шаблону документа. Нарушение: незаполненные поля шаблона, нарушения REST-соглашений, нестандартное использование кодов ответа.

## Свойства набора требований (уровень SET)

- **consistent** — непротиворечивость. Требования не противоречат друг другу, критериям приёмки, дочерним документам; единые термины, единицы, типы.
- **complete** — полнота набора. Покрыты все функции, ошибки, нефункциональные аспекты (безопасность, надёжность, производительность), есть критерии приёмки для каждого требования, заполнены служебные разделы (версия, согласования, откат).
- **traceable** — трассируемость. У требований есть идентификаторы, видна связь «цель → требование → критерий приёмки → API».
- **comprehensible** — понятность набора: единая терминология, нет разночтений в названиях систем.
- **feasible** — выполнимость набора в целом.

- **validatable** — можно валидировать (ISO/IEC/IEEE 29148 п. 5.2.6). По набору можно подтвердить, что продукт решает задачу заказчика: есть цель/проблема, измеримые критерии успеха и приёмки, сценарии. Нарушение: цель не измерима, у функции нет критерия приёмки.
- **ranked** — ранжированность по важности и стабильности (IEEE 830 п. 4.3.5). У требований указан приоритет (обязательно/желательно, MVP/позже) или видно, какие могут измениться. Нарушение: приоритетов нет совсем — непонятно, что резать при нехватке сроков.
- **modifiable** — модифицируемость (IEEE 830 п. 4.3.7). Документ удобно менять: одно правило описано в одном месте, есть структура и нумерация. Нарушение: одно правило повторено в нескольких разделах разными словами (риск расхождения при правке).

## Уровни критичности (поле severity)

- **critical** — два исполнителя по этому тексту гарантированно реализуют или протестируют по-разному, требование невозможно проверить, или есть риск для денег, данных, безопасности (противоречие, нет порога/единицы/условия, неопределённое поведение при ошибке).
- **major** — реализовать можно, но до разработки нужно задать вопрос аналитику; без ответа есть риск переделки.
- **minor** — формулировка, термин, дубль, порядок разделов, нумерация: на код и тесты не влияет.
- Сомневаешься между major и minor — ставь minor.
