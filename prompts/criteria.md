# Критерии качества требований

Источники: ISO/IEC/IEEE 29148:2018 п. 5.2.5 (отдельное требование), п. 5.2.6 (набор требований); IEEE Std 830-1998 п. 4.3.

## Свойства отдельного требования (поле criterion)

- **necessary** — необходимость. Требование нужно для цели продукта; без него чего-то не хватит. Нарушение: требование ни к чему не ведёт, дублирует другое.
- **appropriate** — уместный уровень. Требование говорит «что», а не «как»; нет лишних проектных решений (конкретные технологии, классы, методы HTTP без обоснования). Нарушение: навязанная реализация, которая к тому же ошибочна или рискованна.
- **unambiguous** — однозначность. Формулировку можно понять только одним способом. Нарушение: неопределённые термины («активная карта», «проведённая покупка»), неуказанный часовой пояс, «сумма» без уточнения какая, размытые слова.
- **complete** — полнота. Описаны все условия, граничные случаи, ошибки, единицы. Нарушение: не описано поведение при возврате, при отключении, при ошибке; пустые разделы; пропущены статусы ответа.
- **singular** — единичность. Одно требование — одна мысль. Нарушение: несколько независимых условий в одном пункте, которые нельзя проверить отдельно.
- **feasible** — выполнимость в разумных рамках.
- **verifiable** — проверяемость. Есть объективный способ проверить выполнение (число, порог, точка отсчёта, метод измерения). Нарушение: «в течение минуты» без точки отсчёта и доли событий; нет критериев приёмки.
- **correct** — корректность. Требование верно отражает потребность; пример/значение не ошибочны; описание соответствует сути (например, «сохранение» описано как чтение).
- **conforming** — соответствие стандарту/шаблону документа. Нарушение: незаполненные поля шаблона, нарушения REST-соглашений, нестандартное использование кодов ответа.

## Свойства набора требований (уровень SET)

- **consistent** — непротиворечивость. Требования не противоречат друг другу, критериям приёмки, дочерним документам; единые термины, единицы, типы.
- **complete** — полнота набора. Покрыты все функции, ошибки, нефункциональные аспекты (безопасность, надёжность, производительность), есть критерии приёмки для каждого требования, заполнены служебные разделы (версия, согласования, откат).
- **traceable** — трассируемость. У требований есть идентификаторы, видна связь «цель → требование → критерий приёмки → API».
- **comprehensible** — понятность набора: единая терминология, нет разночтений в названиях систем.
- **feasible** — выполнимость набора в целом.

## Уровни критичности (поле severity)

- **critical** — противоречие, непроверяемость или неполнота, из-за которых разные исполнители реализуют/протестируют по-разному, либо ошибка с риском для денег, данных или безопасности.
- **major** — существенная неясность или пропуск, требующий уточнения у аналитика до разработки.
- **minor** — стилистика, мелкая несогласованность, не мешающая реализации.
