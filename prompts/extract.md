Ты — системный аналитик, который готовит документ требований к ревью.

Задача: разбить документ ниже на отдельные проверяемые требования. Требованием считается любое утверждение, которое обязывает систему или процесс. Пройди по разделам и НИЧЕГО не пропусти:
- Цели — если в них есть ожидание к системе (например, «в момент покупки»).
- Архитектура решения — каждая цепочка систем «A → B → C» отдельно (type=integration).
- Дизайн UI — каждое предложение отдельно (путь к экрану, состав экрана, поведение при ошибке).
- BPMN-схема — цепочка шагов целиком (type=integration).
- Sequence Diagram — КАЖДОЕ сообщение вида «A → B: действие» отдельным требованием (type=integration).
- Функциональные требования (Ф-1…) — КАЖДОЕ предложение-правило отдельным требованием с тем же doc_id (например, у Ф-2 четыре правила — четыре объекта с doc_id «Ф-2»). Не склеивай правила одного пункта: их проверяют по отдельности.
- Нефункциональные требования, требования к данным, интеграции — каждое утверждение.
- Критерии приёмки — каждая строка таблицы отдельно и ЦЕЛИКОМ (исходные условия, действие и ожидаемый результат в одной цитате; не дели строку на ячейки).
- REST-спецификация (часть B): описание назначения метода (строка Description целиком, например «Сохранение порога. Функциональные требования: …»), остальные общие параметры метода, каждый шаг логики, каждое особое правило, каждый параметр запроса и ответа, общие правила раздела (например, какие коды ответа считаются успешными), каждый статус ответа.
Не являются требованиями (не включай): строки чек-листа качества требований («Требование может быть протестировано», «Поддерживается версионность документа» и т.п.), пустой блок согласующих, шапка документа.

Правила:
- quote — ДОСЛОВНЫЙ фрагмент документа (копируй символ в символ, без перефразирования, без markdown-звёздочек). Для строки таблицы бери текст ячеек этой строки как он есть — без заголовков столбцов (Parameter, Format…) и без названия раздела, даже если в PDF они стоят рядом с ячейками. Пример: для строки параметра amount цитата «amount integer 32 bit Да 1 000–1 000 000 Порог в тенге limit_kzt», а НЕ «Parameter Format Size … amount …» — заголовки в документе стоят не рядом с этой строкой, и такая цитата не будет найдена.
- doc_id — идентификатор из документа (например «Ф-1», «Особое правило 2», «Статус 404»), иначе null.
- section — путь к разделу: «Часть A / Функциональные требования».
- type — один из: functional, nonfunctional, data, integration, ui, api, acceptance, other.
- Не объединяй разные требования; не пропускай требования из части B.

Перед тобой ФРАГМЕНТ документа (документ разбит на части). Строки «[Раздел: …]» — служебные метки пути раздела, их не цитируй, используй для поля section.

Ответ — строго JSON-объект без пояснений:
{"items":[{"doc_id":"Ф-1","section":"Часть A / Функциональные требования","quote":"…","type":"functional"}]}
Если во фрагменте нет требований — {"items":[]}.
