# Агент проверки требований

ИИ-агент для статического ревью документа требований до разработки. Он читает документ (PDF, MD, TXT, DOCX), выделяет отдельные требования, проверяет каждое и весь набор по ISO/IEC/IEEE 29148:2018 (п. 5.2.5, 5.2.6) и IEEE Std 830-1998 (п. 4.3) и пишет отчёт на русском.

Кейс: BCC-HUB × MNU FinTech Hackathon, «Агент проверки требований».

## Чем агент отличается

- **Не выдумывает замечаний.** Каждая цитата в замечании ищется в исходном документе; не найденная — отбрасывается, а паспорт отчёта показывает, сколько цитат проверено и сколько отброшено.
- **Качество измерено.** Команда вручную составила эталон из 26 дефектов выданного документа (`eval/golden_defects.json`), скрипт `eval/score.py` считает, сколько из них нашёл агент. Финальный прогон по PDF на `gpt-4.1`: найдено 21 из 26, все 5 критичных — с правильным типом дефекта, отброшенных цитат — 0.
- **Документ может не покидать банк.** С провайдером `ollama` проверка идёт на локальной модели, без отправки текста в облако.
- **Работает на реальных файлах.** PDF (заголовки по размеру шрифта), DOCX, MD, TXT, кодировка Windows-1251; на плохой вход — понятное сообщение и код выхода, а не трассировка.

## Как устроен прогон

```
документ → 1. нарезка на требования (LLM)
         → 2. проверка каждого требования пачками по 6 (LLM)
         → 3. проверка набора целиком: противоречия, пропуски, часть A ↔ API (LLM)
         → + детерминированные правила: пустые разделы, размытые слова
         → 4. проверка цитат: каждая цитата ищется в исходном документе,
              не найденная — отбрасывается (защита от выдуманных замечаний)
         → отчёт .md + машиночитаемый .json
```

У каждого замечания есть дословная цитата и место в документе (строка, для PDF — страница).

В PDF заголовки разделов определяются по размеру шрифта, поэтому нарезка по разделам работает так же, как для Markdown. Пример PDF: `input/requirements.pdf`.

## Установка

Нужен Python 3.10+.

```bash
pip install -r requirements.txt
```

## Ключ LLM

1. Откройте https://console.groq.com/keys и нажмите **Create API Key**. Хватит бесплатного тарифа.
2. Скопируйте пример конфига и вставьте ключ:
   ```bash
   cp .env.example .env        # Windows: copy .env.example .env
   ```
   В `.env` замените `your_groq_key_here` на свой ключ. Файл `.env` в git не попадает.

Модель по умолчанию в `.env.example`: **openai/gpt-oss-120b** через Groq (бесплатно; OpenAI-совместимый API, переменные `OPENAI_*`).

Финальный отчёт в `reports/` получен на **OpenAI `gpt-4.1`** — она точнее классифицирует критичные дефекты. Чтобы повторить, в `.env` укажите:
```dotenv
OPENAI_BASE_URL=https://api.openai.com/v1
OPENAI_API_KEY=<ключ с https://platform.openai.com/api-keys>
OPENAI_MODEL=gpt-4.1
```
Ключ должен соответствовать адресу: ключ OpenAI не работает с адресом Groq и наоборот (ошибка 401 «Invalid API Key»).

Агент работает и с другими провайдерами, переключение одной переменной `LLM_PROVIDER`:
- `openai` — любой OpenAI-совместимый API (Groq, OpenRouter, OpenAI);
- `gemini` — Google Gemini (`GEMINI_API_KEY`, `GEMINI_MODEL`);
- `ollama` — локальная модель (`OLLAMA_MODEL=qwen2.5:14b`), документ не покидает компьютер.

Бесплатный Groq ограничивает 8000 токенов в минуту: агент сам ждёт, сколько просит API, поэтому полный прогон без кэша занимает около 5 минут.

## Запуск

```bash
python -m validator <путь к документу> <путь к отчёту.md>
```

Пример:

```bash
python -m validator input/requirements.md reports/report.md
```

Отчёт ляжет по указанному пути, рядом — `report.json` с теми же данными. Повторный прогон того же документа берёт ответы из кэша и занимает секунды.

### Наглядный отчёт в HTML

Добавьте флаг `--html` или укажите путь отчёта с расширением `.html`:

```bash
python -m validator input/requirements.pdf reports/report.md --html
python -m validator input/requirements.pdf reports/report.html
```

Рядом с `report.md` и `report.json` появится `report.html` — один файл без внешних зависимостей, открывается двойным кликом в браузере, работает без интернета. В нём: вердикт, сводка по критичности, критичные дефекты, поиск и фильтры по критичности и критерию, раскрывающиеся карточки требований, печать в PDF. Светлая и тёмная тема — по настройке системы.
Ответы модели кэшируются в `.cache/`; для чистого прогона добавьте `--no-cache`.

## Если документ не подходит

Агент не падает с трассировкой: причина печатается в консоль **и записывается в файл отчёта** (раздел «Проверка не выполнена»), в `.json` — поле `error`.

| Ситуация | Что делает агент | Код выхода |
| :--- | :--- | :--- |
| Файла нет, путь указывает на папку, файл пустой | сообщает и останавливается | 2 |
| Битый PDF/DOCX, PDF под паролем, PDF-скан без текста | сообщает причину и что сделать (снять пароль, OCR) | 2 |
| Формат не поддерживается (.xlsx, .doc и т.п.), двоичный файл с расширением .md | сообщает поддерживаемые форматы | 2 |
| Нет ключа LLM или провайдер отклонил ключ | сообщает, что настроить в `.env` | 2 |
| Модель не ответила после повторов (сеть, лимиты) | сообщает и останавливается, вывод о документе не делает | 3 |
| В документе не найдено ни одного требования (передан не тот файл) | сообщает и останавливается | 4 |
| Часть страниц PDF без текста, файл не в UTF-8 (читается как Windows-1251), очень большой документ | проверяет и пишет **предупреждение** в паспорт отчёта | 0 |

## Состав отчёта

1. Паспорт прогона: документ, дата, модель, версия агента и коммит, статистика проверки цитат.
2. Нарезка: ID в отчёте — ID в документе — раздел — цитата — место.
3. Проверка каждого требования: критерий, критичность, цитата, проблема, исправление.
4. Проверка всего набора.
5. Сводка: число требований и нарушений, список критичных дефектов.
6. Итог: можно ли начинать разработку и тестирование и что исправить в первую очередь.

## Оценка качества

`eval/golden_defects.json` — эталонный список дефектов выданного документа, составленный командой вручную. Сколько из них нашёл агент:

```bash
python eval/score.py reports/report.json
```

## Структура

```
validator/   код агента (CLI, чтение, LLM, конвейер, отчёт)
prompts/     промпты и каталог критериев
templates/   шаблон отчёта (Jinja2)
eval/        эталон дефектов и скрипт оценки
input/       выданный документ требований
reports/     отчёты прогонов
```
